# TiffinTrack – Solution Reasoning

## 1. Understanding the Problem

The main problem is managing a home-style weekday tiffin subscription service.

A customer subscribes to a monthly tiffin plan and normally receives lunch on weekdays.

The important business rules are:

* Saturdays and Sundays are not delivery days.
* A customer can pause the subscription for travel or festivals.
* Paused days should not be charged.
* Monthly billing should depend on the days actually served.
* The owner needs to know which customers are active and which are paused.
* Customers should be searchable using their phone number.

I designed the system around these rules instead of treating it as a simple CRUD application.

## 2. Data Model Decisions

The main entities are:

* User
* Plan
* Subscription
* PausePeriod
* Notification

A User represents a customer.

A Plan stores the monthly tiffin plan and its price.

A Subscription connects a customer with a plan and stores the subscription start date and status.

PausePeriod stores the start and end dates of a customer's pause.

Notification stores the delivery notification generated by the daily clock.

This separation makes it possible to calculate billing and delivery eligibility using actual subscription and pause data.

## 3. Subscription Rules

A customer cannot create another active or paused subscription if they already have one.

This prevents multiple active subscriptions for the same customer.

When a subscription is created, its status is set to Active.

A subscription can be:

```text
Active
Paused
Cancelled
```

A cancelled subscription cannot be paused or resumed.

Pause periods are also checked for overlapping dates to avoid invalid duplicate pause ranges.

## 4. Billing Logic

The billing logic was implemented in a separate `BillingService`.

For a selected month:

1. The month start and end dates are calculated.
2. The subscription start date is used if it starts after the beginning of the month.
3. Only weekdays are considered eligible delivery days.
4. Weekdays falling inside pause periods are removed.
5. The remaining number of days is treated as delivered days.
6. The monthly plan price is divided by the eligible weekdays.
7. The daily rate is multiplied by the delivered days.

For example, if a plan costs ₹2500 and there are 22 eligible weekdays:

```text
Daily rate = 2500 / 22
```

If the customer was served for 18 days:

```text
Bill = Daily rate × 18
```

This makes the billing directly depend on actual service days.

## 5. Daily Delivery Processing

The daily delivery requirement was implemented using the `/api/clock` endpoint.

The clock first checks whether the selected date is a weekday.

Then it finds active subscriptions.

For each active subscription, the system checks whether the date falls inside a pause period.

If the customer is not paused, the `NotificationService` creates a notification.

The notifications can then be viewed using:

```http
GET /api/outbox
```

This provides a simple way to verify that the notification integration happened.

## 6. Notification Service

Notification creation was separated into `NotificationService`.

The controller is responsible for deciding which customers are eligible.

The service is responsible for creating the notification.

This keeps the controller simpler and makes the notification functionality easier to change later.

For the timed build, notifications are stored in the database as an outbox rather than integrating with a real SMS or messaging provider.

## 7. Frontend Design

The frontend was designed as an owner portal.

The main sections are:

* Overview
* Customers
* Today's Deliveries
* Plans
* Billing
* Import Customers

The dashboard gives the owner a quick view of customers, active subscriptions, paused customers and plans.

The interface was kept simple because the main objective was to make the important business workflows easy to use within the limited build time.

## 8. Backend and Frontend Separation

The frontend communicates with the ASP.NET Core backend using Axios.

The API base URL is kept in:

```text
frontend/src/api.js
```

This avoids repeating the backend URL throughout the application.

React Router is used for navigation between pages.

## 9. Authentication

Registration and login are handled by the backend.

Passwords are not stored as plain text.

BCrypt is used to create password hashes during registration and to verify passwords during login.

The frontend stores the successful login response locally so that the current user information can be used by the application.

For this timed task, a full production authentication system such as refresh-token authentication was not added because the main focus was the subscription business workflow.

## 10. Database Choice

SQLite was selected because this is a timed build and the application does not require a large production database.

Entity Framework Core migrations are used so that the database structure can be created consistently.

The database can be initialized using:

```bash
dotnet ef database update
```

## 11. Testing Process

I tested the backend using Swagger.

The main tests included:

### Registration

Tested:

```http
POST /api/auth/register
```

A test customer was successfully created.

### Login

Tested:

```http
POST /api/auth/login
```

The same customer was successfully authenticated.

### Frontend Login Issue

Initially the frontend login failed.

The browser showed a connection/CORS-type error.

I checked the browser Network tab and found that the frontend was calling:

```text
/auth/login
```

instead of:

```text
/api/auth/login
```

The problem was the Axios base URL.

The API configuration was corrected to include:

```text
/api
```

The project is running in GitHub Codespaces, so the forwarded backend URL was also used instead of relying only on `localhost`.

## 12. Problems Found and Fixed

### Namespace mismatch

Some backend files initially used different namespaces.

The namespaces were standardized to:

```text
TiffinTrack.API
```

### Duplicate DTO definitions

Duplicate authentication and subscription DTO definitions caused compilation problems.

The duplicate definitions were removed and the DTOs were separated into appropriate files.

### Entity and migration issues

Entity Framework migrations were created and applied after fixing model and namespace issues.

### Backend port issue

The backend was running on port:

```text
5088
```

The frontend was initially configured for another port.

The API configuration was updated to use the actual backend port and later the GitHub Codespaces forwarded URL.

### Frontend missing page imports

The React application initially referenced pages that were not created.

The required pages were added so that the router could load correctly.

## 13. Trade-offs

Because the build had a strict time limit, I focused on the main business requirements first.

I preferred:

* Simple architecture
* Clear API endpoints
* SQLite
* Separate services for important logic
* Simple React components
* Swagger testing
* Minimal dependencies

Instead of spending time on advanced authentication, complex state management or production infrastructure.

The goal was to produce a working end-to-end application that demonstrates the core tiffin subscription workflow.
